## 0. 목적과 범위

이 DB의 본체는 **BaTIS(Balanced Trade in Services)** 다. 나라쌍 서비스 교역을 EBOPS 2010 항목별로 담은 유일한 전세계 행렬이고, 연구의 질문은 전부 여기서 나온다. **BIMTS(Balanced International Merchandise Trade Statistics)** 는 같은 OECD가 같은 균형화 철학으로 만든 상품 교역 짝이라 함께 담는다. 상품은 비교군이자 통제군이지 연구 대상이 아니므로, 수집 깊이도 그에 맞춰 차등을 둔다(§4).

두 자료는 KCSDB2의 관세청 자료와 성격이 근본적으로 다르다. 관세청 자료는 신고 원장에 가까운 1차 통계였지만, BaTIS·BIMTS는 **각국 보고치에 추정과 균형화를 얹어 OECD가 만들어 낸 2차 가공물**이다. 이 차이가 아래 모든 설계 판단을 지배한다.

## 1. 실측 확인 사항 (2026-09-16, 이 세션에서 직접 확인)

계획의 근거는 전부 실제 응답으로 확인했다. 확인하지 못한 것은 "미확인"으로 적는다.

### 1.1 BaTIS

| 항목 | 실측값 |
|---|---|
| 판(edition) | BPM6, **December 2025** (WTO 표기 `BPM6-1`) |
| 기간 | 2005–2024 (20년) |
| 경제 | 보고국 205 · 상대국 208 (코드표 기준 개별 203 + 그룹 3: WL 세계, EU, GEU) |
| 항목 | 31 (표준 EBOPS 2010 27개 + 파생 4개: SOX, SOX1, SPX1, SPX4) |
| 관측치 수 | **100,951,234** (SDMX 메타 `obs_count`) |
| 단위 | **백만 USD**, 소수 포함 |
| 배포 1 (권장) | `https://webfs-sdd.oecd.org/files/.Stat/BATIS/OECD-WTO_BATIS_BPM6_December2025_bulk.zip` — **489.6 MB**, 안에 CSV + codes.xlsx 2개, **Range 지원(재개 가능)** |
| 배포 2 (미러) | `https://www.wto.org/english/res_e/statis_e/daily_update_e/OECD-WTO_BATIS_data_BPM6-1.zip` — 508.8 MB, CSV 1개, Range 지원, Last-Modified 2025-12-08 |
| 압축 해제 | CSV 1개 `OECD-WTO_BATIS_BPM6_December2025_bulk.csv` = **2.98 GB** (zip 중앙디렉터리에서 실측) |
| 부속 | 코드표 xlsx(39 KB), 방법론 PDF(1.1 MB) |

벌크 CSV의 열은 코드표의 예시 표에서 확인된다. `Reporter | Partner | Flow | Item_code | Year | Reported_value | Final_value | Methodology | Balanced_value` 아홉 개다. 값이 셋이라는 점이 이 자료의 핵심이다.

- `Reported_value` — 통계당국이 실제로 보고한 값(세계 총계에 맞춰 재척도된 것 포함). **없는 셀이 많다.**
- `Final_value` — 보고치에 OECD·WTO의 추정·조정을 더해 내부 정합을 맞춘 값.
- `Balanced_value` — 수출과 거울상 수입을 화해시킨 값. 정의상 `Balanced(A→B, 수출) = Balanced(B→A, 수입)`.
- `Methodology` — 그 셀이 어떻게 만들어졌는지의 25개 코드(`R_NAT` 보고, `M1.1`~`M2.3` 중력모형 추정, `E8.x` 보간, `M8.3` ROW 귀속 등).

같은 자료가 OECD SDMX API로도 나온다. 차원은 `REF_AREA, COUNTERPART_AREA, TRADE_FLOW, PRODUCT_TYPE, SERVICE, FREQ, UNIT_MEASURE, ADJUSTMENT`이고 `ADJUSTMENT`의 `N/F/B`가 각각 Reported/Final/Balanced에 대응한다. 실제 질의(한국, 2020–2024 전량)는 12.8 MB·125,130행이 한 번에 돌아왔다. 다만 전량을 API로 받으면 200회 넘는 호출이 되므로 **본 수집은 벌크 파일로 하고 API는 교차검증에만 쓴다**(§6 B8).

### 1.2 BIMTS

| 항목 | 실측값 |
|---|---|
| 기간 | 1995–2024 (30년) |
| 경제 | 수출국 203 · 수입국 203 |
| 분류 | HS2017 2D(97개 장)·4D·6D(약 5,200개), CPA 2.1 2D(57개) |
| 값의 종류 | **균형치 둘뿐** — `B`(총 균형치), `B_ADJ_RX`(재수출 조정 균형치, OECD 권장) |
| 방향 | `REF_AREA`=**수출국**, `COUNTERPART_AREA`=수입국. 균형화 결과라 한 흐름이 한 번만 기록된다 |
| 결측 규약 | **0 거래는 행 자체가 없다**(OECD가 "`..`로 표기, 파일 크기 축소" 명시) |
| 관측치 수 | 2D **49,921,840** · CPA 2.1 **38,270,861** (4D·6D는 메타 서비스가 500으로 응답, 미확인) |
| 단위 | 백만 USD |

벌크 파일은 데이터 탐색기의 관련 파일(annotation `EXT_RESOURCE`)로 공개되고, 크기는 다음과 같이 실측했다.

| 파일 | 형식 | 크기 |
|---|---|---|
| `HS17_2D_DE_1995_To_2024.zip` | CSV(쉼표) | 590.8 MB |
| `HS17_4D_DE_Parquet_1995_To_2009.zip` | Parquet | 942.4 MB |
| `HS17_4D_DE_Parquet_2010_To_2024.zip` | Parquet | 1,269.8 MB |
| `HS17_6D_DE_Parquet_1995_To_2005.zip` | Parquet | 1,925.4 MB |
| `HS17_6D_DE_Parquet_2006_To_2013.zip` | Parquet | 1,775.0 MB |
| `HS17_6D_DE_Parquet_2014_To_2019.zip` | Parquet | 1,479.5 MB |
| `HS17_6D_DE_Parquet_2020_To_2024.zip` | Parquet | 1,272.7 MB |
| 4D·6D CSV판 | CSV(파이프 구분) | 같은 구간별로 1.2~1.6 GB씩, 총 ~9 GB |

OECD readme는 4D·6D에 대해 parquet을 권한다(스내피 압축 열지향이라 선택적 읽기가 가능). 6D 파일에는 **수출국·수입국 각각에 대해 "보고됨 / 보고 후 조정됨 / 미보고·추정됨"을 구분하는 플래그**가 붙는다고 명시돼 있다 — 2D에는 없는 정보이고, 추정분을 걸러 내야 하는 연구라면 이것이 6D를 받는 유일한 이유가 된다.

### 1.3 두 자료의 결정적 비대칭

BaTIS는 보고치(`Reported_value`)를 함께 준다. **BIMTS는 주지 않는다** — 배포되는 값은 균형치 둘뿐이다. 따라서 상품 쪽에서 "보고치 대 균형치"를 비교하는 연구는 이 DB만으로 불가능하고 UN Comtrade 원자료가 따로 필요하다(이미 `C:\Work\Projects\UNComtraade`가 있다). 이 DB는 그 경계를 흐리지 않는다.

## 2. 원칙 (KCSDB2 승계 + 이 자료에 맞춘 수정)

### 승계하는 것

1. **fact는 원본 필드만 담는다.** 파생 컬럼을 만들지 않는다.
2. **관측값을 변형하지 않는다.** 단위 환산(백만→달러), 반올림, 결측의 0 대체를 하지 않는다.
3. **연결·참조는 dim에서 한다.** 국가코드 체계 대응, 항목명, 방법론 코드 설명은 dim으로 분리하고 fact는 건드리지 않는다.
4. **계층 분리.** DB는 raw 보존과 무결성 검증까지. 집계·비중·성장률·추정분 제거는 분석 계층의 일이다.
5. **정직한 NULL.** 없으면 없는 대로 둔다.
6. **검증은 단일 스크립트 하나로.** PASS/WARN/FAIL 리포트를 남긴다.
7. **임시 파일은 스크래치패드로, 원본은 `data/raw`에 보존.**

### 이 자료 때문에 새로 세우는 것

8. **판(edition)을 1급 키로 둔다.** OECD는 새 판을 낼 때 **과거 연도까지 통째로 다시 추정한다.** 2005년 값도 판마다 달라진다. URL은 그대로인데 내용이 바뀌므로, `edition` 컬럼을 모든 fact의 키에 넣고 받은 zip 원본과 SHA-256을 `data/raw/<edition>/`에 영구 보존한다. KCSDB2가 10일 잠정치를 `fetched_at`으로 쌓아 둔 것과 같은 이유다 — 나중에 "그때 알 수 있었던 값"으로 재현할 수 있어야 한다.
9. **추정의 흔적을 반드시 함께 담는다.** `Methodology`, `OBS_STATUS`, 6D 플래그는 부가 정보가 아니라 이 자료의 본질이다. 세계 서비스 교역의 약 35%만이 실제로 나라쌍으로 보고되고 나머지는 중력모형 추정이다. 추정분을 걸러 낼 수 없는 DB는 이 자료에 대해 쓸모가 없다.
10. **정수 캐스팅 금지.** KCSDB2에서는 관세청이 정수 달러를 주므로 `int()`가 무손실이었다. 여기서는 백만 달러 단위 실수이므로 원본 문자열의 유효숫자를 그대로 `DOUBLE`에 싣는다.
11. **0과 결측을 원본 규약대로 구분한다.** BaTIS는 0 행이 존재할 수 있고, BIMTS는 0을 아예 행으로 만들지 않는다. **우리가 0을 채워 넣지 않는다.** 이 차이는 dim이 아니라 문서(§7)와 검증(§6 M5)이 지킨다.
12. **BPM5판을 섞지 않는다.** WTO가 배포하는 1995–2012 BPM5판은 국제기준이 달라 연결이 불가능하다(WTO 자신이 경고). 필요하면 별도 표로 두되 이번 범위에서는 받지 않는다.

## 4. 수집 범위 — 단계로 나눈다

BaTIS는 전량이 당연하고, BIMTS는 깊이를 고를 수 있다. 용량이 두 자릿수 배로 갈리므로 단계를 끊는다.

| 단계 | 대상 | 내려받기 | DuckDB 예상 | 판단 |
|---|---|---|---|---|
| **1** | BaTIS 전량 (2005–2024, 31항목, 값 3종) | 490 MB | 3~5 GB | **필수.** 연구 본체 |
| **2** | BIMTS HS2017 2D + CPA 2.1 | 0.6 GB + α | 2~4 GB | **권장.** 상품 대조군으로 충분. 장(chapter) 해상도면 서비스와의 비교 분석은 다 된다 |
| **3** | BIMTS HS2017 4D | 2.2 GB | 10~20 GB | 보류. 품목 수준 질문이 실제로 생기면 |
| **4** | BIMTS HS2017 6D (+보고/추정 플래그) | 6.5 GB | 30 GB 이상, 수억 행 | 보류. 6D를 받는 이유는 해상도가 아니라 **플래그**다 |

3·4단계의 DuckDB 예상은 압축 해제 크기에서 외삽한 추정이다. 실제 착수 시에는 6D 파일 하나(1995–2005)만 먼저 풀어 행수·열 구성을 재고 나서 나머지를 정한다.

권고는 **1단계 + 2단계**다. 서비스가 핵심이고 상품은 짝이라면 HS 2단위로 충분하다. 현재 C 드라이브 여유는 528 GB이므로 4단계까지 가도 물리적 제약은 없다. 제약은 용량이 아니라 적재·검증에 드는 시간과, 6D를 넣는 순간 DB가 "가볍게 배포할 수 있는 자산"이기를 그만둔다는 점이다.

## 5. 테이블 설계 (초안)

### fact

**`fact_batis`** — 벌크 CSV를 열 이름만 소문자로 바꿔 그대로 싣는다. 값 셋을 한 행에 두는 것은 원본이 그런 형태이기 때문이다(넓은 형태로 바꾸거나 긴 형태로 펴지 않는다).

| 컬럼 | 출처 | 비고 |
|---|---|---|
| edition | 파일명 | `2025-12`. **유일하게 허용하는 파생** |
| reporter | Reporter | 2자 코드 원본 |
| partner | Partner | 2자 코드 원본 |
| flow | Flow | `X`/`M` |
| item_code | Item_code | EBOPS 2010 |
| year | Year | |
| reported_value | Reported_value | 백만 USD, NULL 있음 |
| final_value | Final_value | 백만 USD |
| methodology | Methodology | 25개 코드 |
| balanced_value | Balanced_value | 백만 USD |

**`fact_bimts_hs2`** (2단계) — `edition, exporter, importer, hs2, year, adjustment, obs_value, obs_status, methodology_type`. 원본이 `ADJUSTMENT` 차원을 가진 긴 형태이므로 긴 형태로 싣는다. `B`와 `B_ADJ_RX`를 열로 펴지 않는다.

**`fact_bimts_cpa2`** (2단계) — 같은 구조, 분류만 CPA 2.1.

**`fact_bimts_hs4` / `fact_bimts_hs6`** (3·4단계) — 같은 구조 + 6D는 수출국·수입국 플래그 열 추가. 6D는 연도 범위별 parquet을 그대로 두고 DuckDB에서 뷰로 붙이는 방안(원본 parquet을 DB에 복사하지 않음)도 적재 시 비교한다.

### dim

- **`dim_area`** — BaTIS 2자 코드와 OECD SDMX 3자 코드를 한 표에서 잇는다. `code_batis, code_iso3, name_en, area_type(c/g), note`. 매칭 안 되는 코드(`ANT_F` 구 네덜란드령 안틸레스, `SDN_F` 구 수단, `SACU` 등)는 참조 컬럼을 NULL로 둔다. 교정하지 않는다.
- **`dim_service`** — `item_code, description, item_type(s 표준/d 파생), derivation`. 파생 4개의 산식(`SOX = S − SL` 등)이 문자열로 들어오므로 검증(§6 B2)의 근거가 된다.
- **`dim_methodology`** — BaTIS 25개 코드와 설명. 보고/추정/조정의 대분류 열을 **우리가 하나 덧붙인다**(`R_*`→보고, `M*`→모형추정, `E*`→파생·보간). 이것은 dim이므로 원칙 위반이 아니다.
- **`dim_hs2017`, `dim_cpa21`** — OECD SDMX 코드표(`CL_PRODUCT_HS2017` 6,905개, `CL_PRODUCT_CPA_2_1` 5,566개)에서 받는다. 2·4·6단위가 한 표에 있으므로 `level` 열로 구분한다.
- **`dim_obs_status`, `dim_methodology_type`** — SDMX 부가 코드표.
- **`dim_edition`** — 판 이력. `dataset, edition, released, url, bytes, sha256, fetched_at, rows`. 다음 판이 나왔을 때 무엇이 바뀌었는지 말할 수 있는 유일한 근거다.

**연계표(concordance)는 만들지 않는다.** BIMTS는 OECD가 이미 전 기간을 HS2017로 변환해 배포하고, BaTIS는 EBOPS 2010 하나로 고정돼 있다. KCSDB2에서 HS 개정 연계에 들인 노력이 여기서는 필요 없다 — 대신 **"OECD가 변환했다"는 사실 자체와 그 방법론 문서를 `data/external`에 보존**한다. 우리가 통제하지 못한 변환이 자료 안에 이미 들어 있다는 점은 분석 계층이 알아야 한다.

## 6. 검증 항목

`06_validate.py` 하나로 통합한다. 값 기준(금액)과 개수 기준을 함께 본다 — KCSDB2의 "봉인2" 교훈대로 개수만 보면 착시가 생긴다.

### BaTIS

- **B1 대칭성**: `balanced(A,B,X,i,t) == balanced(B,A,M,i,t)` 전 행. 정의적 항등이므로 불일치가 있으면 그 자체가 발견이다. 불일치 행수와 최대 절대차를 남긴다.
- **B2 파생항목 재계산**: `SOX = S − SL`, `SOX1 = SE+SF+SG+SH+SI+SJ+SK`, `SPX1 = SOX1 + SL`, `SPX4 = SA + SB`. 코드표의 산식대로 계산해 대조.
- **B3 표준항목 합 대 총계**: `SA+…+SL == S` 여부를 값의 종류(N/F/B)별로 따로 본다. **보고치에서는 안 맞는 것이 정상**이고, 얼마나 안 맞는지가 자료의 성질이다.
- **B4 하위 합**: `SC1+SC2+SC3+SC4 == SC`, `SDA+SDB == SD`, `SI1+SI2+SI3 == SI`, `SJ1+SJ2+SJ3 == SJ`, `SK1+SK2 == SK`.
- **B5 그룹 코드 정합**: 파트너 `WL`(세계) 행이 개별 파트너 합과 어떤 관계인지, `EU`·`GEU`가 개별국과 중복되는지 확인해 **분석 계층이 중복 집계하지 않도록 문서에 못 박는다.**
- **B6 보고 커버리지**: `reported_value IS NOT NULL` 비율을 연도×항목×보고국으로 집계. 이 표 자체가 연구 자산이다.
- **B7 방법론 분포**: `methodology`별 행수와 금액 비중을 연도×항목으로. 추정분 비중이 결과 해석에 직결된다.
- **B8 SDMX 교차검증**: 무작위 200개 슬라이스를 API로 다시 받아 벌크와 대조. 벌크 판과 API 판이 같은 판인지 확인하는 유일한 방법이다.
- **B9 코드 매칭률**: `reporter`·`partner` → `dim_area`, `item_code` → `dim_service`, `methodology` → `dim_methodology`.

### BIMTS

- **M1 총계 정합**: `_T == Σ(HS 챕터)`를 `adjustment`별로.
- **M2 파트너 총계**: 파트너 `W == Σ(개별 파트너)`.
- **M3 해상도 간 정합**: 4D·6D를 받으면 `Σ 6D == 4D`, `Σ 4D == 2D`.
- **M4 재수출 조정**: `B_ADJ_RX <= B`가 성립하는 범위와 예외를 센다(재배분이므로 개별 셀에서는 커질 수 있다 — 세계 총계에서 확인).
- **M5 결측 규약 확인**: 값이 정확히 0인 행이 존재하는지 센다. OECD 설명대로면 0이어야 한다.
- **M6 기간 연속성**: 1995–2024 빠진 해 없음.

## 7. 알려진 함정 (실측으로 확인한 것만)

- **SDMX의 6D 엔드포인트는 현재 500을 뱉는다.** 키 형태를 여러 가지로 바꿔도 같다(2026-09-16 실측). 2D·CPA는 정상. **6D는 파일로만 받을 수 있다.**
- **`stats.oecd.org/wbos/fileview2.aspx`(BIMTS 관련 파일)는 HEAD에 405를 주고 Range를 무시한다.** 이어받기가 안 되므로 끊기면 처음부터다. 1~2 GB짜리를 여러 개 받아야 하니 재시도 로직과 부분 파일 검증이 필요하다. 반면 `webfs-sdd.oecd.org`(BaTIS)와 WTO는 Range를 지원한다.
- **국가코드 체계가 둘이다.** BaTIS 벌크는 2자(`KR`), SDMX는 3자(`KOR`). 한쪽으로 통일하지 말고 `dim_area`에서 잇는다.
- **그룹 코드 중복 집계.** `WL`, `EU`, `GEU`, `ROW`가 개별국과 같은 열에 섞여 있다. 필터 없이 합치면 세계 교역이 두 배가 된다.
- **BIMTS는 0 행이 없다.** "그 해에 교역이 없었다"와 "자료가 없다"가 구분되지 않는 것이 아니라, OECD가 0을 결측으로 표기한 것이다. 시계열을 만들 때 0으로 채우는 것은 분석 계층의 선택이며 DB는 채우지 않는다.
- **BIMTS는 수출국 기준 단일 기록이다.** 수입국 관점의 질의는 방향을 뒤집어야 하고, 수입국이 보고한 값은 애초에 배포되지 않는다.
- **판 갱신이 조용히 일어난다.** URL은 고정, 내용만 교체된다. `00_probe_source.py`가 크기·Last-Modified·해시를 주기적으로 대조해 알린다.
- **WTO 미러와 OECD 미러의 크기가 다르다**(508.8 MB 대 489.6 MB). OECD판에 코드표 xlsx가 함께 들어 있고 WTO판은 CSV 단독이다. 데이터 CSV 자체가 동일한지는 받은 뒤 해시로 대조한다. **OECD판을 정본으로 삼는다.**
- **BPM5판과 BPM6판은 연결 불가.** 같은 이름의 파일이 나란히 배포되므로 URL을 혼동하지 말 것.

## 8. 실행 순서

1. **골격 생성** — 폴더, `requirements.txt`(duckdb, pandas, pyarrow, requests, openpyxl), `config/settings.yaml`. 인증키는 필요 없다(둘 다 공개, 키 불요).
2. **`00_probe_source.py`** — 두 미러의 헤더·크기, BIMTS 관련 파일 목록(SDMX dataflow annotation에서 자동 추출), SDMX 판 정보를 찍고 `dim_edition` 후보 행을 만든다. 이 단계에서 이 문서 §1의 수치를 재확인한다.
3. **1단계 수집·적재** — BaTIS zip 수집 → 해시 기록 → CSV 청크 읽기로 parquet 변환(2.98 GB를 한 번에 메모리에 올리지 않는다) → DuckDB 적재 → §6 BaTIS 검증 전항목 → 결과를 `docs/DB_구축_원칙.md`로 승격 작성.
4. **2단계 수집·적재** — BIMTS 2D + CPA 2.1. 같은 절차. 검증 M1·M2·M4·M5·M6.
5. **현황·문서화** — `07_db_status.py`로 표 목록·행수·기간·출처를 자동 생성, README 작성.
6. **(선택) 3·4단계** — 6D 파일 하나를 먼저 풀어 실측한 뒤 결정.

1·2단계는 각각 반나절 규모다(내려받기 시간이 대부분). 4단계로 가면 적재·검증에 하루 이상을 따로 잡아야 한다.

## 9. 결정이 필요한 것

1. **BIMTS 깊이** — 2D+CPA까지(권고), 4D까지, 6D까지 중 어디서 멈출 것인가. 6D의 유일한 명분은 해상도가 아니라 보고/추정 플래그다.
2. **상품 쪽 보고치** — BIMTS가 균형치만 주므로, 상품에서 보고치 대 균형치 비교가 연구 질문에 포함되면 UN Comtrade를 이 DB에 함께 넣을지 아니면 기존 `UNComtraade` 프로젝트에 남길지.
3. **부수 자료** — 서비스 교역 연구라면 WTO TiSMOS(공급 형태별 서비스 교역, 같은 WTO 벌크 페이지)와 OECD STRI(서비스 교역 제한지수)가 자연스러운 짝이다. 이번 범위 밖으로 두었으나 초기에 넣으면 dim 설계가 달라진다.

## 10. 실행 중 밝혀진 정정 (2026-09-16 같은 날 수집 실행)

계획을 세운 뒤 실제로 받아 보니 §1·§7의 몇 가지가 틀렸다. 확정 사실은
`DB_구축_원칙.md`에 옮기고, 여기에는 계획이 어디서 어긋났는지만 남긴다.

- **두 미러는 같은 파일이 아니다.** OECD판은 열 12개(성질 열 셋이 더 있다)에 **ISO3
  코드**(`KOR`)와 `EXP`/`IMP`, 방법론 37코드다. WTO판은 열 9개에 2자 코드(`KR`)와
  `X`/`M`, 방법론 24코드다. 국가 그룹도 다르다(OECD판에 `OECD`·`EU27_2020`이 있다).
  **OECD판이 넓으므로 정본으로 삼았다.** 2자·3자 코드 대응표는 필요 없어졌다.
- **BIMTS도 이어받기가 된다.** 데이터 탐색기 화면의 `fileview2.aspx` 링크만 HEAD·Range가
  막혀 있고, 같은 파일이 `webfs-sdd.oecd.org`에도 있으며 그쪽은 Range를 지원한다.
  파일 목록은 SDMX 데이터흐름의 `EXT_RESOURCE` 주석에서 읽어 오므로 우리가 URL을
  적어 둘 필요도 없다(`02_fetch_bimts.py`).
- **동봉 코드표가 자료와 어긋난다.** 코드표의 `WLD`·`RWD`·`E_EU`·`ANT`·`SCG`는 자료에
  없고, 자료의 `W`·`WXD`·`WXOECD`·`WXEU27_2020`·`ANT_F`·`SCG_F`는 코드표에 없다.
  그래서 `dim_area`를 세 출처(자료의 성질 열·코드표·SDMX CL_AREA) 병렬로 만들었다.
- **CPA 2.1도 벌크 파일이 있다**(`CPA_2D_DE_1995_To_2024.zip`, 690.7 MB). SDMX로 긁을
  필요가 없었다.

## 11. 인용·라이선스

OECD는 2024년 7월 1일 이후 콘텐츠에 **CC BY 4.0**을 기본 적용한다. BaTIS는 OECD·WTO 공동 산출물이므로 WTO 이용약관도 함께 확인해 README에 출처 문구를 고정한다. 방법론 PDF(BaTIS·BIMTS 각 1건)를 `data/external`에 함께 보존하고, 연구 문서에서는 판(December 2025)을 반드시 명시한다 — 판이 바뀌면 수치가 바뀌기 때문이다.
